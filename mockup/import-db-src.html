三类来源 · 可信度从高到低
*.sql 脚本 —— 真 CREATE TABLE，字段/主键/外键/注释最全，跟「粘贴 DDL」走同一套解析器。
@Entity 实体类 —— 从 @Column / 驼峰转下划线推字段和注释；类型映射是猜的，但实体一般照着表写，可信。
Mapper XML —— 只认 resultMap / insert 里出现过的列，没出现的拿不到。 只有 XML 来源的表标 ⚠️不完整 并默认不勾 —— 少字段是安静的错，比报错难查。
同名表被多个来源命中时按上面的顺序合并，来源记进 data_source （PRD §7.3 的 UNIQUE(table_name, data_source) 就是给这留的位）。

设计取舍 · 待你拍板 PRD §6.1 / §7.6 / §7.8
1 · 密码不进连接列表。历史只存主机 / 端口 / 库名 / 用户。测试/本地可记系统凭据；生产每次现输。
2 · 只读边界。MVP 放行 MySQL 且整个会话只跑 information_schema 元数据查询， 连上后界面明示「只读」。PG / Oracle 禁用并写明原因，有真需求再开。
3 · 两步拉取。先一次查询拿全量表清单，勾选后才逐表拉字段， 不勾的不取 —— 这是 PRD §7.8「首次导入 50 张 < 10 秒」的达成方式。
4 · 增量语义待拍板。已缓存的表现在标「覆盖」，导入即整表替换（跟方式一一致）。 PRD §7.6 还提了「无变化自动跳过」，那要做字段级 diff —— 值不值？
5 · 扫描可信度顺序：*.sql > @Entity > Mapper XML。 只有 XML 来源的表标不完整、默认不勾 —— 跟外键两级可信度同一个哲学：推断出来的东西不许悄悄混进结果。
6 · 扫描防护。跳过二进制和超大文本、文件数上限、固定排除构建目录； 超限停下来让你缩小范围，绝不把 IDE 卡死。
